# Spec 004 — Scene pipeline: open studio lane `st10_terrain` → `st45_validate`
Status: Clarified
Tier: M · Parent: 000-foundation · Approved: —
Supersedes/Modifies: (none)

## 1. Intent
Every RTX render, sensor scan, physics run and web 3D view of PitStudio starts from one OpenUSD pit scene built from
real terrain. This spec covers the five scene stages of the open studio lane (`studio/`, Python 3.14, CPU only):
`st10_terrain` (USGS 3DEP Bingham Canyon DEMs and LAZ tiles → a site-local terrain grid, level-of-detail meshes, tiles
and a USD terrain layer; McKinley and Hambach optional), `st20_pit_design` (benches, berms, ramps, windrows and a haul-road
network regenerated by design code and labelled as such, with a cut/fill volume report), `st30_assets` (procedural
machines and people with UsdPhysics and semantic labels, CC0 materials), `st40_compose` (the root stage with sublayers,
variant sets, a scene manifest and a scene digest) and `st45_validate` (`usd-validation-nvidia`, `simready-validate`, the
scene invariants and the build-twice hash). It serves developers who want a reproducible, validated scene, and every
downstream stage (physics, sensors, synthetic data, Kit review, web export) that must see the same geometry and labels.
Out of scope: downloading the data (`s00_download`, spec 008), the ultimate-pit shells and pushback optimisation (spec
017), the glTF / 3D Tiles bake and its parity test (`s60_export`, the export stage), the Kit check `st45b_kit_validate`
(NVIDIA Kit lane), rendering, and the runner's locks, cache and manifests (spec 002).

## 2. User stories
### US-004-1 (P1) Real terrain in the site frame
As a developer, I want the Bingham Canyon DEMs and lidar tiles turned into a metre-based, Z-up, site-local terrain grid
and meshes whose coordinate systems are read from the files, so that every engine sees the same real ground. Independent
test: run `st10_terrain` on the committed fixture tiles and check the grid, the CRS record, the mesh error bound and the
USD layer metadata.

### US-004-2 (P1) Benches regenerated by design code, and labelled
As a mining engineer, I want benches, berms, ramps and windrows generated from declared design parameters and labelled
"regenerated by design code, not observed", so that coarse scenes are honest and their geometry obeys the design
code. Independent test: run `st20_pit_design` on a circular fixture pit and check bench heights, ramp grade, windrow
height, the provenance label and the cut/fill volumes against hand calculation.

### US-004-3 (P2) Licence-clean, labelled, articulated assets
As a data/AI practitioner, I want procedural machines and people with physics joints and a closed semantic-label
vocabulary, built only from our code and CC0 inputs, so that synthetic labels are exact and redistributable.
Independent test: build the fleet and check articulation trees, masses, labels and the licence of every texture.

### US-004-4 (P1) One composed scene with a manifest
As a developer, I want one root stage per case with fixed sublayers and variant sets, a scene manifest and a scene
digest, so that physics, sensors, synthetic data and the web export consume the same scene. Independent test: compose
the fixture scene and validate the manifest and the digest against their schemas.

### US-004-5 (P1) Validated and deterministic
As a reviewer, I want every scene validated by the open validators and the scene invariants and built twice with
identical hashes, so that a published scene is trustworthy and reproducible. Independent test: run `st45_validate` on
the fixture scene on Windows and Linux; the report passes and the two builds hash identically.

## 3. Functional requirements (EARS)
Every stage rejects bad input before it reads pixels or points or allocates large arrays, writes into its run's temporary
folder and lets the runner promote outputs only after they validate (spec 002). The error classes named below are
written by the stage as the prefix of its stage-result message (`<class>: <detail>`), with the stage result's
`error_class` set to `unknown` (spec 002's stage protocol); they are deterministic, so the runner never retries them.
Lengths are metres, angles degrees, grades percent (rise over run × 100).

### 3.1 `st10_terrain`
| ID | Pattern | Requirement | Verification |
|---|---|---|---|
| FR-004-01 | Ubiquitous | `st10_terrain` shall read the horizontal CRS, the vertical CRS and the axis units of every DEM (GeoTIFF keys) and LAZ tile (WKT VLR) from the file's own metadata, never from a default, and shall record them as EPSG codes (or the WKT when no code exists) in the scene manifest. | unit |
| FR-004-02 | Ubiquitous | `st10_terrain` shall express all terrain outputs in the site-local frame: X east, Y north, Z up, in metres, relative to the recipe's site origin (EPSG code of its UTM zone, easting, northing, elevation z₀), computed in float64 and stored as float32 offsets whose absolute value is ≤ 1.0 × 10⁵ m horizontally and ≤ 5.0 × 10³ m vertically. | unit |
| FR-004-03 | Event | When an input's horizontal or vertical unit is the US survey foot or the international foot, `st10_terrain` shall convert it to metres with the exact factors 1200/3937 m and 0.3048 m respectively, and shall record the factor applied. | unit |
| FR-004-04 | Event | When LAZ tiles are the terrain input, `st10_terrain` shall keep only points of ASPRS class 2 (ground), grid them at the declared cell size (default 1.0 m) as the per-cell mean elevation computed with an order-independent summation (points sorted by cell and elevation before a float64 sum), and mark cells without a ground point as nodata. | unit |
| FR-004-05 | Event | When nodata cells form a 4-connected hole of at most `max_fill_cells` cells (default 16), `st10_terrain` shall fill it with the discrete harmonic (Laplace) interpolant of the surrounding valid cells, set the cell's bit in a fill mask, and leave larger holes as nodata, excluded from meshes and counted in the scene manifest. | unit + property |
| FR-004-06 | Ubiquitous | `st10_terrain` shall build one right-triangulated irregular network (RTIN) mesh per level of detail from (2ᵏ + 1)² grid tiles, such that the vertical distance between the mesh and every valid grid sample is ≤ the LOD's declared `max_error` (defaults 0.25, 1.0 and 4.0 m for LOD 0–2). | property |
| FR-004-07 | Ubiquitous | `st10_terrain` shall split each LOD into a quadtree of tiles of 257 × 257 grid samples, give adjacent tiles identical vertex positions on every shared edge (after the RTIN of both tiles is forced to include the edge vertices of either), add skirts of the declared depth (default 2 × `max_error`), and write a tile index (tile id, LOD, bounding box, `max_error`, vertex and triangle counts, SHA-256). | property |
| FR-004-08 | Ubiquitous | `st10_terrain` shall write the terrain as a USD layer (`terrain.usdc`, one `lod` variant per LOD) with `upAxis = "Z"`, `metersPerUnit = 1.0` and `kilogramsPerUnit = 1.0` authored explicitly, a `SemanticsLabelsAPI` class label `terrain` on every mesh prim, and the attributes `pitstudio:source_id`, `pitstudio:project`, `pitstudio:epoch` and `pitstudio:attribution` carrying the dataset card's attribution text. | unit |
| FR-004-09 | Optional | Where the recipe enables the McKinley source and an OpenTopography key is configured in the environment, or enables the Hambach DGM1 source, `st10_terrain` shall process that AOI with the same rules; where an enabled optional source is unavailable, it shall record that source as "not run (\<reason\>)" in the scene manifest and still complete the Bingham terrain. | integration |
| FR-004-10 | Unwanted | If a DEM or LAZ input is corrupt (invalid header, truncated file, LAZ chunk-table or decompression error, a point count different from the header, a GeoTIFF that cannot be decoded) or its SHA-256 differs from the data registry entry, then `st10_terrain` shall fail with error class `input-corrupt` naming the source id and the tile, write no output and raise within 5 s of opening that file. | unit (hostile) |
| FR-004-11 | Unwanted | If an input has no CRS, or two inputs differ in horizontal CRS (including datum realisation, e.g. NAD83 vs NAD83(2011)) or in vertical datum without a transformation declared in the recipe, then `st10_terrain` shall fail with error class `crs-mismatch` listing both CRSs and the inputs that carry them. | unit (hostile) |
| FR-004-12 | Unwanted | If an elevation is NaN, ±inf, equal to the file's nodata sentinel, or outside [−500, 9000] m after unit conversion, then `st10_terrain` shall treat that sample as nodata (never as a height) and count it, and if the nodata fraction inside the AOI after hole filling exceeds `max_nodata_frac` (default 0.05), it shall fail with error class `too-much-nodata` reporting the fraction. | unit (hostile) |
| FR-004-13 | Unwanted | If the AOI is empty, not a valid polygon (fewer than 3 vertices, self-intersecting, zero area), outside the extent of every input, or would produce more than `max_cells` grid cells (default 1.0 × 10⁸), then `st10_terrain` shall fail with error class `aoi-invalid` or `aoi-too-large` before reading any pixel or point. | unit (hostile) |
| FR-004-14 | Unwanted | If an input path handed to the stage by its job specification resolves outside the store or the data root (`..` segments, another drive, a UNC path, a symbolic link leaving the root), or the file's SHA-256 differs from the digest in the job specification, then the stage shall fail with error class `input-path` or `input-corrupt` before reading it. | unit (hostile) |
| FR-004-15 | Unwanted | If the AOI has not been confirmed against a mine-polygon dataset (Tang & Werner, or Maus) with at least 90 % of the mine polygon's area inside the AOI, then `st10_terrain` shall write the site name in the scene manifest with the suffix " (provisional)". | unit |

### 3.2 `st20_pit_design`
| ID | Pattern | Requirement | Verification |
|---|---|---|---|
| FR-004-16 | Ubiquitous | `st20_pit_design` shall generate the benches from a pit outline (a closed polygon in the site frame, from a terrain contour at the declared rim elevation or from an upstream shell) and the declared design parameters — bench height H, face angle α, berm width b, ramp grade g, ramp width W, windrow height — as per-bench crest and toe polygons, where each toe is its crest offset inward by H / tan α and each next crest is the toe offset inward by b (mitre joins), down to the declared floor elevation. | unit |
| FR-004-17 | Ubiquitous | `st20_pit_design` shall generate one helical ramp from the rim to the floor whose centreline grade, sampled at ≤ 1 m spacing, is ≤ g + 0.1 % everywhere, whose width is ≥ W everywhere, and whose centreline is one connected polyline; benches crossed by the ramp shall be widened by W. | unit + property |
| FR-004-18 | Ubiquitous | `st20_pit_design` shall place windrows on the outer edge of the ramp and of every berm with a height ≥ the mid-axle height of the largest haul unit declared in the recipe (30 CFR 56.9300(b)), and shall record both heights in the design report. | unit |
| FR-004-19 | Ubiquitous | `st20_pit_design` shall carve the design into the terrain as z_final = min(z_terrain, z_design) inside the pit outline (windrows added on top), and shall write a design report with, per bench, crest and toe elevations, measured bench height, face angle, berm width, and in total the cut volume V_cut, the fill volume V_fill and the identity residual of P-004-07. | unit |
| FR-004-20 | Ubiquitous | `st20_pit_design` shall mark every prim it generates with `pitstudio:provenance = "design-code"` and the scene manifest's design layer entry with the label "regenerated by design code, not observed". | unit |
| FR-004-21 | Event | When `st20_pit_design` completes, it shall write the haul-road network (ramp centreline and bench roads) as a GeoJSON graph in the site frame, one LineString per edge with its length (m) and mean and maximum grade (%), every node connected to the pit exit. | unit |
| FR-004-22 | Unwanted | If a design parameter is non-finite or outside its hard domain (H ∈ [5, 30] m, α ∈ [40°, 85°], b ∈ [3, 60] m, g ∈ [0, 15] %, W ∈ [8, 60] m, windrow height ∈ (0, 5] m), or outside the design-code range the recipe declares with its citation, or an inward offset collapses a bench polygon before the floor is reached, then `st20_pit_design` shall fail with error class `design-infeasible` naming the parameter or the bench index, and shall never clip geometry silently. | unit (hostile) |
| FR-004-23 | Unwanted | If the pit outline is not a closed simple polygon, has fewer than 3 vertices, has an area below (2W)², or lies partly outside the terrain grid, then `st20_pit_design` shall fail with error class `outline-invalid`. | unit (hostile) |

| FR-004-39 | Unwanted | If the two builds differ in any layer hash, then `st45_validate` shall fail with error class `nondeterministic`, listing the differing layers and the first differing line of their text export. | unit (hostile) |

## 4. Correctness properties
| ID | Property (for all …) | Input domain / generator | Tolerance |
|---|---|---|---|
| P-004-01 | For any height grid of (2ᵏ + 1)² samples and any `max_error` > 0, the RTIN mesh interpolates every valid sample within `max_error`. | Hypothesis: k ∈ 3..8, fractal (fBm) and stepped-bench grids, heights in [−1000, 1000] m, `max_error` ∈ [0.05, 8] m | `max_error` + 2.5 × 10⁻⁴ m (float32 vertex rounding at \|z\| ≤ 1000 m) |
| P-004-02 | For any pair of adjacent tiles at the same LOD, the vertex positions on the shared edge are identical (watertight). | Hypothesis: random grids 513², split into 4 tiles, every LOD | exact (bitwise float32) |
| P-004-03 | Translation invariance: shifting all inputs by (Δx, Δy, Δz) in the source CRS and the site origin by the same vector yields the same site-local grid. | Hypothesis: Δx, Δy ∈ [−5000, 5000] m, Δz ∈ [−100, 100] m, fixture DEM | atol 1.0 × 10⁻³ m |
| P-004-04 | Unit-change invariance: the same terrain supplied in US survey feet (horizontal and vertical) or in metres yields the same site-local grid. | fixture DEM re-encoded in feet; Hypothesis over cell sizes 0.5–4 m | atol 1.0 × 10⁻³ m |
| P-004-05 | Permutation invariance: any permutation of the LAZ tile order and of the point order within tiles yields a bitwise-identical terrain grid. | Hypothesis: random permutations of a 2 × 10⁴-point fixture | exact |
| P-004-06 | For any planar surface z = a·x + b·y + c with any hole of ≤ `max_fill_cells` cells, the harmonic fill reproduces the plane. | Hypothesis: a, b ∈ [−1, 1], c ∈ [−500, 500] m, random hole shapes | atol 1.0 × 10⁻⁶ m (float64 solve) |
| P-004-07 | Volume conservation: V_cut − V_fill = Σ_cells (z_terrain − z_final) · ΔA exactly, and for a circular benched pit on flat ground V_cut equals the hand-calculated sum of conical frustums within the rasterisation bound Σ_k P_k · Δx · H (P_k the crest perimeter of bench k). | identity: Hypothesis over outlines and parameters in the hard domain; analytic: rim radius 500 m, H = 15 m, α = 70°, b = 10 m, 10 benches, Δx = 1 m | identity: rtol 1 × 10⁻¹² (float64); analytic: the bound and ≤ 1 % |
| P-004-08 | Rotation invariance: rotating the pit outline by any angle θ about the site origin rotates every crest and toe polygon by θ and leaves every volume and bench measure unchanged. | Hypothesis: θ ∈ [0°, 360°), convex and concave outlines | Hausdorff ≤ 1 × 10⁻⁶ × outline extent; volumes rtol 1 × 10⁻⁹ before rasterisation |
| P-004-09 | Monotonicity: with the rim outline and floor fixed, increasing the face angle α never decreases V_cut, and increasing the berm width b never increases V_cut; the overall slope angle atan(H / (H / tan α + b)) is non-decreasing in α and non-increasing in b. | Hypothesis: pairs of parameter sets in the hard domain differing in one parameter | exact ordering (computed on the vector geometry, before rasterisation) |
| P-004-10 | For any feasible outline and parameters, the maximum ramp centreline grade is ≤ g + 0.1 % and the minimum ramp width is ≥ W. | Hypothesis: outlines from random star polygons, parameters in the hard domain | as stated |
| P-004-11 | Build determinism (child of P-000-01): for any seed and parameters, two builds produce identical layer and stage hashes. | Hypothesis: seeds ∈ [0, 2³²), the fixture scene | exact |
| P-004-12 | Label completeness: for any composed scene, every geometry prim has exactly one class label from the vocabulary and no label attribute is time-sampled. | Hypothesis: random fleets (0–20 machines, 0–30 people) on the fixture scene | exact |

## 7. Edge cases and assumptions
- **Pinned constants.** 30 CFR 56.9300(b): "Berms or guardrails shall be at least mid-axle height of the largest
  self-propelled mobile equipment which usually travels the roadway" (read on the Cornell LII copy of 30 CFR 56.9300,
  paragraph (b)). Foot factors: US survey foot = 1200/3937 m, international foot = 0.3048 m (definitions).
- **UNVERIFIED** (kept out of every oracle): the customary ramp grade of about 8–10 % and two-way ramp width of about
  3–3.5 truck widths (USBM IC 8758, Kaufman & Ault 1977 — the copy found returned HTTP 404), and the bench height
  12–15 m and bench width 20–40 m (secondary source only). The recipe declares the design-code ranges it uses with a
  citation and verification status; the spec checks the generated geometry against the declared values and the hard
  sanity domain of FR-004-22, never against these unverified numbers.
- The Bingham query box is hand-typed; the site name stays provisional until FR-004-15 confirms it.
- The 2013 DEM covers the box only partly; the 2018 and 2023 DEMs are the default epochs. LAZ projects (2006, 2018, 2023,
  Wasatch Fault) are never merged into one surface; one recipe names one project per terrain grid.
- USGS publishes no checksum for these files; the SHA-256 is pinned at first download by the data pipeline.
- `.usdc` byte determinism is not established; binary layers are compared through their flattened text export.
- Kit 110 reads an older OpenUSD (25.11) than `usd-core` 26.8; Kit compatibility is the Kit lane's check, not this spec's.
- Elevation hard range [−500, 9000] m bounds Earth's land surface with margin; it catches sentinel values such as
  −3.4 × 10³⁸ and −9999 that a file forgot to declare.
- Hole filling stops at 16 cells (16 m² at 1 m) so that it never invents terrain at a scale that matters to a bench
  (≥ 5 m high, ≥ 3 m wide); larger gaps stay nodata and are visible as holes.
- Volumes are in m³ on the site grid; tonnage needs a density and is out of scope.

## 8. Clarifications log
- Resolved: gridding of ground points uses the per-cell mean with an order-independent sum (P-004-05) rather than a TIN
  interpolation; TIN-based gridding was rejected as order- and tie-dependent.
- Resolved: hole filling is harmonic (exact on planes), not GDAL inverse-distance filling (not exact on planes).
- Resolved: the docs list `st10_terrain` with lock "none or `gpu0.compute`"; this spec makes every scene stage CPU-only
  (NFR-004-03). A later GPU acceleration would be a spec change.
- Resolved: the docs describe a dual writer (USD and glTF from one `SceneSpec`) with a parity test. The glTF writer and
  the parity test belong to the export stage; this spec defines the `SceneSpec` (DC-004-01) and the scene digest
  (DC-004-08) that the parity test compares against.
- Resolved: `st45b_kit_validate` (Kit lane) is not part of this spec; an `incomplete` Kit check does not change this
  stage's report.
- Resolved: "mass/volume conservation of cut/fill" is the exact discrete identity of P-004-07 plus the analytic benched
  pit; tonnage is out of scope.
- Resolved: the design-code ranges are recipe data with citations; the spec fixes only a hard sanity domain.
- Resolved: sublayer order puts the terrain weakest so that design, fleet and animation layers can override it.
- Resolved (alignment with spec 002): stages receive inputs as paths with digests in the runner's job specification
  and report through its stage result, whose `error_class` enum is closed; this spec's error classes therefore travel
  as the message prefix (§3 preamble), and FR-004-14 checks the job-specification paths and digests. Recipes never
  hold paths (spec 001).
- Resolved: an incomplete validation fails `st45_validate` (FR-004-38) instead of marking the scene unpublishable,
  because publication belongs to spec 002 and generated USD is never published; downstream stages then do not run.
- Resolved: the docs name weather once as a layer (studio stages) and once as a variant set (OpenUSD page); both are
  kept: a `weather` sublayer holds the weather prims and a `weather` variant set selects the condition.
- Integration 2026-10-07: draft schema written for DC-004-01 … DC-004-08 (`specs/004-scene-pipeline/contracts/`, valid
  and hostile examples indexed in `examples/index.json`); DC-004-01 is a recipe `params` object (keys `param_key`,
  depth ≤ 4, no `$schema`, strings ≤ 256); closed vocabularies chosen: 15 class labels (`terrain`, `bench`, `berm`,
  `ramp`, `windrow`, `haul_road`, the seven machine classes, `person`, `boulder` as in spec 009), 18 part labels, the
  eight registry ids a scene uses, `time_of_day` and `weather` names, LOD 0–2 (`lod0`–`lod2`); pushback and scenario
  names are free identifiers; the defaults `max_fill_cells` 16, `max_nodata_frac` 0.05 and `max_cells` 1.0 × 10⁸ are
  also caps (stricter reading); a design parameter is {value, design-code min/max, citation, verification}; wheeled
  machines must declare a mid-axle height; bounds where the spec gives none: cell size 0.25–10 m, UTM-zone EPSG codes,
  dimensions ≤ 50 m, masses ≤ 2 × 10⁶ kg, ≤ 64 instances per model and ≤ 64 people, tiles ≤ 67,077 vertices and
  ≤ 133,120 triangles (257² samples plus skirts), 10 MB = 10,000,000 bytes; measured values in the design and validation

  status is `pending` until `st45_validate` runs; the road network keeps site-frame coordinates (foreign member

  cover the mesh buffers held in `terrain.usdc`; validator severities are normalised to `error`, `warning`, `info`; the
