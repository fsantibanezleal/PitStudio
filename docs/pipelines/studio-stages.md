> one builds, with which tool, how long it is expected to take, and which of its results may be published. · Part of:

## What and why

The studio is where PitStudio uses the GPU for more than training: it builds an OpenUSD pit from real lidar, simulates
bulk material and tailings, renders RTX images and sensor data, generates labelled synthetic data, trains robot
policies and asks a vision-language model about pit safety. Each tool family lives in its own uv environment, because
their pins conflict (Python 3.14 for the open stack, Python 3.12 and a fixed PyTorch for the NVIDIA runtimes). Stages
hand data to each other and to the pipeline as **files only**, validated by schemas on both sides, so the 3.12 and 3.14
environments never share a process.

Two licence facts run through this page:

- Stages that run **Kit, Isaac Sim, Replicator or ovrtx** carry `performance: local-only`. Their outputs are published;
  their timings, throughput and GPU telemetry are not, because the NVIDIA Software License Agreement §8.9 forbids
  disclosing performance data without permission [1].
- NVIDIA binaries, assets and caches never leave the machine. Published renders show our own procedural scenes with
  CC0 materials and MakeHuman CC0 people ([Sources and licences](../data-contract/sources-and-licences.md)).

## Open studio lane: `studio/` (Python 3.14)

Locked tools (`studio/uv.lock`): `usd-core` 26.8, `warp-lang` 1.17.0, `newton` 1.6.0, `mujoco-warp` 3.12.0,
`usd-validation-nvidia` 1.22.0, `simready-validate` 2026.8.0, `laspy` 2.7.0, `rasterio` 1.5.2, `pyproj` 3.8.0, `trimesh`
5.1.1, `ortools` 9.15.6755, `zarr` 3.4.0, `pynvvideocodec` 2.2.3, `nvidia-ml-py` 13.615.71, `nvtx` 0.2.16. FFmpeg 8.1
(LGPL build) is an external tool.

| Stage | Runtime (estimate) | What it does | Outputs | GPU lock | Determinism |
|---|---|---|---|---|---|
| `st10_terrain` | 10–40 min | real lidar and DEMs → cropped, gridded terrain; meshes per level of detail | terrain grids and meshes, USD terrain layer | none or `gpu0.compute` | `bitwise` |
| `st20_pit_design` | minutes | benches, ramps and haul roads regenerated by design code from the pit geometry (labelled as such) | design layer, road network | none | `bitwise` |
| `st30_assets` | minutes | procedural trucks, shovel, excavator, people from MakeHuman CC0 exports, CC0 materials | asset USD files | none | `bitwise` |
| `st40_compose` | minutes | the root stage: terrain / design / fleet / sensors / weather layers, variant sets, physics and semantic labels | composed USD stage | none | `bitwise` |
| `st45_validate` | minutes | `usd-validation-nvidia` and `simready-validate` checks; build-twice hash | validation report, stage hash | none | `bitwise` |
| `st50_physics` | 1–2 scenarios per hour | Warp DEM (Hertz–Mindlin), Newton implicit MPM, Warp shallow water (tailings), dust particles, vehicles | Zarr fields, Parquet observables, replay frames | `gpu0.compute` | `bitwise` (deterministic Warp) or `statistical` (MPM) |
| `st56_encode` | ~1–5 min per clip pair incl. the VMAF search | NVENC AV1 1080p + H.264 720p through FFmpeg 8.1, VMAF-targeted bitrate | MP4 pair ≤ 25 MB, WebP poster, encoder record | `gpu0.nvenc` | `bitwise` given the frames |

Notes:

- **Encoding needs FFmpeg 8.1.** FFmpeg 9.x builds use NVENC SDK 13.1 headers, which need driver ≥ 610; FFmpeg 8.1
  builds use the SDK 13.0 headers, which need driver ≥ 570 [2][3]. FFmpeg refuses to encode when the build's NVENC API is
  newer than the driver's, with no fallback [4].
- **Deterministic Warp kernels** use Warp's deterministic mode for atomic operations (added in 1.15.0) when their
  results feed parity or golden checks; the cost is measured once [5].

## NVIDIA rendering lane: `studio/isaac/` (Python 3.12)

Locked: `isaacsim[all,extscache]` 6.1.0.0, `torch` 2.11.0 (Isaac Sim's own pin), `mujoco-usd-converter`. The
environment uses uv-managed interpreters only, never the Microsoft Store shim. Isaac Sim 6.1.0 was **tested** on
Windows driver 595.97 [6], while Isaac Sim 6.0.0 lists Windows driver 581.42 [14]; the Isaac Sim Compatibility Checker
on the reference machine decides between 6.1.0 and 6.0.0.1.

| Stage | Runtime (estimate) | What it does | Outputs | Performance |
|---|---|---|---|---|
| `st52_rtx_render` | minutes per clip | RTX renders of case scenes (lossless PNG / EXR sequences) | frame sequences + frame manifest | local-only |
| `st54_vehicles` | minutes per clip | PhysX vehicles as the visual twin of the traffic case | clips, trajectories | local-only |
| `st55_sdg` | ~3–11 h per 20k images (measured locally) | Replicator synthetic data: COCO boxes, instance masks, depth; structured and unstructured domain randomisation | labelled image shards | local-only |
| `st57_rain_lidar` | minutes per scenario (measured locally) | Isaac Sim lidar in rain | point-cloud shards | local-only |

Replicator writers include COCO and basic writers with RGB, 2-D boxes, instance and semantic segmentation and depth;
headless capture is driven by `rep.orchestrator.step` [7]. Rendered frames are encoded by `st56_encode`, not by Kit's
movie capture, whose MP4 settings are undocumented [8].

## RTX sensor lane: `studio/rtx/` (Python 3.12)

Locked: `ovrtx` 0.5.0.377615, `ovstage` 0.2.0.377349, `ovphysx` 0.6.3 (all pre-release, from NVIDIA's package index),
never imported in the same process as Kit or Isaac Sim.

| Stage | Runtime | Sensors | Outputs | Performance |
|---|---|---|---|---|
| `st53_sensors` | throughput unpublished upstream; measured locally | S1 truck lidar with our dust and rain model; S2 drone survey camera; S3 crusher camera; S4a 77 GHz proximity radar | point clouds, images, radar detections with Doppler | local-only |

A per-frame point-count guard stops the stage on an empty lidar frame: an open ovrtx issue reports that the lidar
silently returns 0 points for a wide or near-pole elevation fan on Windows with exactly the pinned versions [9]. The
elevation fan is limited to a tested range.

## Robot-learning lane: `studio/isaaclab/` (Python 3.12, optional)

Isaac Lab 3.0 (BSD-3), pinned to the `v3.0.0-EA` tag, used kit-less on Newton.

| Stage | Runtime (estimate) | What it does | Outputs |
|---|---|---|---|
| `st60_il_train` | IL-1 1–4 h; IL-2 2–8 h; IL-3 2–3 h (optional) | PPO policies: haul truck on a real ramp with light-vehicle avoidance; excavator digging in FEE soil; loader (optional) | policies (ONNX < 1 MB), learning curves, rollouts |
| `st61_il_mpm_eval` | — | zero-shot check of the dig policy in Newton implicit MPM | FEE → MPM fill gap with 95 % CI |

The lane is optional: it may end as "evaluated, not adopted", and no headline result depends on it
([Isaac Lab policies](../models/isaac-lab-policies.md)).

## Scene-review lane: `studio/kit/`

Only our own Kit extension lives in the repository; USD Composer / Explorer applications are generated from NVIDIA's
`kit-app-template` outside the repository, because template output carries NVIDIA licence headers [10].

| Stage | Runtime (estimate) | What it does | Performance |
|---|---|---|---|
| `st58_kit_capture` | minutes per waypoint at N samples per pixel (measured locally) | headless path-traced captures from our waypoints (lossless frames for `st56_encode`) | local-only |
| `st45b_kit_validate` | minutes | the composed stage opened and checked in Kit | local-only |

## Vision-language lane: `studio/reason/`

llama.cpp b11381 (MIT) is an external tool; the model is our own GGUF Q8_0 conversion of the official Cosmos Reason 2
(2B) revision, with a transformers BF16 reference [11].

| Stage | What it does |
|---|---|
| `st59_reason_bench` | footprint, speed and Q8_0-vs-BF16 agreement on binary questions |
| `st59a_vqa` | hazard questions with answers computed from the USD scene |
| `st59b_plausibility` | two-alternative plausibility judgements on pairs of our simulations |
| `st59c_captions` | captions of synthetic frames, scored for hallucination |

Outputs are text, published display-only with "Built on NVIDIA Cosmos"; the weights stay local
([Cosmos Reason 2](../models/cosmos-reason-2.md)).

|---|---|

## Assumptions and limits

- Runtimes are plan estimates. The ones marked "measured locally" belong to licence-restricted tools; they are recorded
  in local manifests and never published.
- Pre-release NVIDIA libraries (ovrtx, ovstage, ovphysx, Isaac Lab EA) can change their APIs; thin adapters and exact
  pins contain that risk, and a lane that fails its smoke test is documented as "evaluated, not adopted".
- A 16 GB laptop GPU sits at the minimum Isaac Sim lists [6]; scenes stay at ≤ 720p with one or two cameras, and the
  open lane carries every core result.

## In PitStudio

- **Code paths:** `studio/src/pitstudio_studio/{scene,physics,media,telemetry}`, `studio/isaac/src/pitstudio_isaac/`,
  `studio/rtx/src/pitstudio_rtx/`, `studio/isaaclab/src/pitstudio_isaaclab/` (package skeletons exist today).
- **Status:** environments are locked; no stage has run. The Isaac Sim, ovrtx, Isaac Lab, llama.cpp and MakeHuman smoke
  probes run after the machine's GPU hold is lifted.

```bash run deferred=P6
uv run --extra runner studio run studio/recipes/<case>.yaml --stage st50_physics
uv run --extra runner studio run studio/recipes/<case>.yaml --stage st56_encode
```
